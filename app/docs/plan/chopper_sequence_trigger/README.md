# Chopper Sequence Trigger Source

## Goal
Make the chopper/profile sequence advance source explicit and controllable through the shell.

## Non-Goals
This plan does not tune the position PI controller, persist trigger selection, or implement the external index source on anything other than the existing TIM2 input-capture path.

## Current Problem
The profile sequence had `motor profile seq trigger source`, but the `timer/internal` path was a decimated ADC/control-loop tick. That was ambiguous and unsuitable now that the chopper wheel needs a clear distinction between shell-fired test advances, a real internal hardware timer, and an external index pulse.

## Design
The profile sequence has exactly one active trigger source selected by shell:

- `internal`: TIM5 CH1 compare interrupt generated by the project `mcpwm` driver. `motor profile seq period_ms <ms>` programs the TIM5 period through a runtime `mcpwm_set_period_ns()` API. Aliases `timer` and `tim5` are accepted.
- `external`: TIM2 CH1 / PA0 input capture for the external index pulse. The existing `edge`, `channel`, and `min_interval_us` settings apply only to this source. Aliases `tim2` and `index` are accepted.
- `software`: manual shell source for deterministic tuning. It never advances automatically. `motor profile seq trigger fire` advances exactly one target while the sequence is running. Alias `manual` is accepted.

Devicetree aliases bind the hardware roles instead of hard-coding timer node labels in the shell implementation:

```dts
profile-seq-internal = &profile_seq_timer;  /* TIM5 mcpwm */
profile-seq-external = &triggers;           /* TIM2 input capture */
```

The state-machine event path remains shared. Timer/capture ISRs only enqueue `MOTOR_EVENT_PROFILE_SEQ_TICK`; the online position state plans the actual move.

## Implementation Phases
Phase 1:
Add TIM5 `mcpwm` devicetree node and timer-role aliases.

Phase 2:
Add runtime period setting to the `mcpwm` API/STM32 driver.

Phase 3:
Update profile sequence shell source handling for `internal`, `external`, and `software`.

Phase 4:
Remove the old ADC/control-loop synthesized internal tick source.

Phase 5:
Update operator documentation and validate with unit/build checks.

## Acceptance Criteria
`motor profile seq trigger source internal`, `external`, and `software` are accepted.

`motor profile seq trigger status` reports `INTERNAL`, `EXTERNAL`, or `SOFTWARE` unambiguously.

`motor profile seq period_ms <ms>` updates the TIM5 period for the internal source.

`motor profile seq trigger fire` is accepted for `software` and `external`, and rejected for `internal`.

Starting an `internal` sequence arms TIM5 CH1 and does not use ADC/control ISR tick synthesis.

Starting a `software` sequence arms playback without issuing an automatic tick.

## HIL Evidence
No live motor motion is required for this implementation. Hardware validation before position tuning should use:

```text
motor profile seq trigger source software
motor profile seq trigger status
motor profile seq trigger source internal
motor profile seq period_ms 1000
motor profile seq trigger status
motor profile seq trigger source external
motor profile seq trigger channel 0
motor profile seq trigger status
```

## Risks
TIM5 is managed by the project `mcpwm` driver in timer-only mode. If later firmware needs TIM5 for another function, move the internal source by changing the `profile-seq-internal` devicetree alias and the mcpwm timer node.

The internal source uses compare interrupts, not a physical output pin. That is intentional for profile sequencing; external hardware synchronization should use TIM2 CH1.
